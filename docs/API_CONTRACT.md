# Контракт и проверочный список ТЗ

Источник: предоставленное задание «Тестовое Junior Python FastAPI».
Чекбоксы отмечают реализованные и проверенные сценарии. Реализованы чтение
тарифов и платежей, создание платежа с идемпотентностью и банковский вебхук.

## Маршруты

`api/api_v1` — внутренняя структура кода. Публичного префикса `/api/v1` нет.

| Метод и путь | Запрос | Результат |
| --- | --- | --- |
| `GET /tariffs` | Без тела | `200`: список `{id, title, price}` |
| `POST /payments` | `tariff_id`, `email`, `method`, необязательные `installment_months`, `promo_code`; необязательный заголовок `Idempotency-Key` | `201`: новый платёж; `200`: существующий платёж с тем же ключом; `404`: тариф не найден |
| `GET /payments/{id}` | Идентификатор платежа | `200`: платёж; `404`: платёж не найден |
| `GET /payments` | Необязательные query-параметры `email`, `status` | `200`: список платежей с полями из ТЗ; без совпадений — `[]` |
| `POST /webhooks/bank` | `payment_id`, `status` | `200 {"result":"ok"}`; `404`: платёж не найден; `409 {"error":"invalid_transition"}`: переход запрещён |

Ошибки валидации возвращают стандартный ответ FastAPI с кодом `422`.
Тело ошибки `404` ТЗ не фиксирует. Формат `409` фиксирован: поле `error`
находится в корне, без обёртки `detail`.
Банковский вебхук требует подпись `X-Signature`; отсутствующая или неверная — `401`.

Фильтр `email` проверяется как email и использует точное совпадение.
`status` принимает `pending`, `succeeded`, `failed`, `refunded`.
Вместе фильтры применяются через AND; без фильтров возвращаются все платежи.
Порядок списка — по возрастанию `id`, неверные фильтры дают стандартный `422`.

## Ответ с платежом

| Поле | Значение |
| --- | --- |
| `id` | Идентификатор платежа |
| `status` | `pending`, `succeeded`, `failed`, `refunded` |
| `tariff_id` | Идентификатор тарифа |
| `amount` | Итоговая сумма к оплате, целое число копеек |
| `discount` | Сумма скидки, целое число копеек |
| `method` | `card`, `sbp`, `installment` |
| `installment_months` | Срок рассрочки: 3, 6, 12; без рассрочки — `null` |
| `schedule` | Список целых сумм в копейках; без рассрочки — `null` |
| `email` | Email плательщика |
| `created_at` | Время создания платежа |

Сумма, скидка, график и начальный статус определяются сервером.
Ключ идемпотентности в ответ не входит. Дополнительные ограничения на вход,
которых нет в ТЗ, без отдельного решения не вводятся.

## Деньги, тарифы и валидация

- [x] При запуске существуют `basic=990000`, `standard=1990000`, `premium=2990000`.
- [x] Повторный и конкурентный запуск не создаёт дубли тарифов.
- [x] Все суммы в API, расчётах и БД — целые копейки, без `float`.
- [x] Без промокода скидка равна нулю, сумма равна цене тарифа.
- [x] `KVITTO10` даёт скидку 10%, регистр не важен.
- [x] Для `standard` с промокодом: `discount=199000`, `amount=1791000`.
- [x] Неизвестный промокод возвращает стандартную ошибку `422`.
- [x] Проверяются email и допустимые способы оплаты.
- [x] Для `installment` обязателен срок 3, 6 или 12; иначе `422`.
- [x] Для каждого срока длина графика совпадает со сроком, сумма — с `amount`.
- [x] Остаток распределяется по первым платежам; даты платежей не добавляются.
- [x] `standard` без скидки на 3 месяца: `[663334, 663333, 663333]`.

Схемы и расчёты проверены отдельно и через `POST /payments`.
Неизвестный промокод даёт стандартный `422` без записи в БД.
Промокоды хранятся в словаре «код → процент скидки», изначально `KVITTO10 → 10`.
Скидка рассчитывается как `price * percent // 100`: дробная часть копейки отбрасывается.
Для `card` и `sbp` переданный допустимый срок приводится к `null`.

## Создание и идемпотентность

- [x] Новый платёж создаётся со статусом `pending`, ответ — `201`.
- [x] Без ключа каждый корректный запрос создаёт отдельный платёж.
- [x] Повтор одного ключа возвращает прежний платёж с `200`, без дубля.
- [x] Одновременные запросы с одним ключом создают ровно одну запись в БД.
- [x] Уникальность ключа обеспечена ограничением PostgreSQL.

Сервис управляет транзакцией; CRUD выполняет `INSERT ... ON CONFLICT DO NOTHING`
только для конфликта ключа идемпотентности. После конфликта отдельный SELECT
читает сохранённый платёж при стандартном для PostgreSQL READ COMMITTED.
Повтор с валидным телом возвращает прежний платёж без пересчёта сумм,
даже если переданы другие параметры. Успешное создание логируется после commit
без email, тела запроса и ключа идемпотентности.

Вебхук читает платёж через `SELECT ... FOR UPDATE` внутри транзакции сервиса.
После ожидания блокировки проверяется актуальный статус; отказ откатывает
транзакцию и возвращает `409 {"error":"invalid_transition"}` без `detail`.
Успешная смена статуса логируется после commit без персональных данных.
Тесты проверяют полную запись БД и реальное ожидание блокировки PostgreSQL
для конкурирующих и одинаковых уведомлений.

## Бонусы и границы

Запуск через Docker Compose с PostgreSQL и управление сессиями реализованы.
Модели БД, начальная миграция Alembic и создание тарифов реализованы.
Реализованы `GET /tariffs` и `GET /payments/{id}` без префикса `/api/v1`.
Создание платежа, идемпотентность и банковский вебхук реализованы.
Собственные правила для ассистента уже представлены в `AGENTS.md`.

- [x] Приложение ожидает готовности PostgreSQL и проверяет подключение при старте.
- [x] Пароль БД берётся из окружения; `.env` не входит в образ.
- [x] Один engine на lifespan, отдельная сессия на запрос, engine освобождается.
- [x] Границы транзакций определены: сервис использует `session.begin()`, CRUD не коммитит.
- [x] Реальные тесты PostgreSQL проверяют commit, rollback и конкурентные сессии.

Бонусы `GET /payments` с фильтрами и HMAC-подпись вебхука реализованы.
GitHub Actions пока не реализован.

- [x] `X-Signature` проверяется как HMAC-SHA256 исходных байтов тела.
- [x] Сравнение выполняется через `hmac.compare_digest` до изменения БД.
- [x] Отсутствующая или неверная подпись даёт `401` и не меняет БД.
- [x] Отсутствующий или пустой `WEBHOOK_SECRET` запрещает запуск.

`WEBHOOK_SECRET` — обязательный непустой секрет из окружения или локального `.env`.
Значение из пробелов также запрещено. В `.env.example` оставлено пустое поле;
Compose требует задать секрет и передаёт его приложению и процессу миграций.
В репозиторий, образ и логи секрет не включается.

Подпись — 64 шестнадцатеричных символа без префикса `sha256=`. Дубли заголовка
отклоняются. HMAC вычисляется по исходным байтам до разбора JSON и открытия
сессии БД. Пробелы, переносы строк и порядок полей влияют на подпись:
после вычисления подписанное тело нужно отправлять без изменений.

Пример расчёта на стороне отправителя (секрет совпадает с настройкой сервера):

```python
import hmac
import os

import httpx

body = b'{"payment_id":123,"status":"succeeded"}'
signature = hmac.digest(
    os.environ["WEBHOOK_SECRET"].encode("utf-8"), body, "sha256"
).hex()
response = httpx.post(
    "http://localhost:8000/webhooks/bank",
    content=body,
    headers={"Content-Type": "application/json", "X-Signature": signature},
)
```

При верной подписи действуют обычные ответы `200`, `404`, `409`, `422`.
Неверная подпись всегда даёт `401 {"detail":"Invalid signature"}`, включая
повреждённый JSON. У подписанного запроса повтор того же статуса остаётся `409`.

Фронтенд, авторизация пользователей, настоящий банк и деплой вне объёма задания.
Публикация репозитория и отправка ссылки не выполняются без отдельного разрешения.
