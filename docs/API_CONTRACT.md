# Контракт и проверочный список ТЗ

Источник: предоставленное задание «Тестовое Junior Python FastAPI».
Чекбоксы отмечают реализованные и проверенные сценарии. Доступны маршруты
чтения тарифов и платежа; создание платежа и вебхук ещё не реализованы.

## Маршруты

`api/api_v1` — внутренняя структура кода. Публичного префикса `/api/v1` нет.

| Метод и путь | Запрос | Результат |
| --- | --- | --- |
| `GET /tariffs` | Без тела | `200`: список `{id, title, price}` |
| `POST /payments` | `tariff_id`, `email`, `method`, необязательные `installment_months`, `promo_code`; необязательный заголовок `Idempotency-Key` | `201`: новый платёж; `200`: существующий платёж с тем же ключом |
| `GET /payments/{id}` | Идентификатор платежа | `200`: платёж; `404`: платёж не найден |
| `GET /payments` | Необязательные query-параметры `email`, `status` | `200`: список платежей с полями из ТЗ; без совпадений — `[]` |
| `POST /webhooks/bank` | `payment_id`, `status` | `200 {"result":"ok"}`; `404`: платёж не найден; `409 {"error":"invalid_transition"}`: переход запрещён |

Ошибки валидации возвращают стандартный ответ FastAPI с кодом `422`.
Тело ошибки `404` ТЗ не фиксирует. Формат `409` фиксирован: поле `error`
находится в корне, без обёртки `detail`.

Фильтр `email` проверяется как email и использует точное совпадение.
`status` принимает `pending`, `succeeded`, `failed`, `refunded`.
Вместе фильтры применяются через AND; без фильтров возвращаются все платежи.
Порядок списка — по возрастанию `id`, неверные фильтры дают стандартный `422`.

## Ответ с платежом

| Поле | Значение |
| --- | --- |
| `id` | Идентификатор платежа |
| `status` | `pending`, `succeeded`, `failed`, `refunded` |
| `tariff_id` | Идентификатор тарифа |
| `amount` | Итоговая сумма к оплате, целое число копеек |
| `discount` | Сумма скидки, целое число копеек |
| `method` | `card`, `sbp`, `installment` |
| `installment_months` | Срок рассрочки: 3, 6, 12; без рассрочки — `null` |
| `schedule` | Список целых сумм в копейках; без рассрочки — `null` |
| `email` | Email плательщика |
| `created_at` | Время создания платежа |

Сумма, скидка, график и начальный статус определяются сервером.
Ключ идемпотентности в ответ не входит. Дополнительные ограничения на вход,
которых нет в ТЗ, без отдельного решения не вводятся.

## Деньги, тарифы и валидация

- [x] При запуске существуют `basic=990000`, `standard=1990000`, `premium=2990000`.
- [x] Повторный и конкурентный запуск не создаёт дубли тарифов.
- [ ] Все суммы в API, расчётах и БД — целые копейки, без `float`.
- [x] Без промокода скидка равна нулю, сумма равна цене тарифа.
- [x] `KVITTO10` даёт скидку 10%, регистр не важен.
- [x] Для `standard` с промокодом: `discount=199000`, `amount=1791000`.
- [x] Неизвестный промокод возвращает стандартную ошибку `422`.
- [x] Проверяются email и допустимые способы оплаты.
- [x] Для `installment` обязателен срок 3, 6 или 12; иначе `422`.
- [x] Для каждого срока длина графика совпадает со сроком, сумма — с `amount`.
- [x] Остаток распределяется по первым платежам; даты платежей не добавляются.
- [x] `standard` без скидки на 3 месяца: `[663334, 663333, 663333]`.

Схемы и расчёты проверены отдельно; стандартные ошибки `422` — через тестовый
маршрут FastAPI. Создание платежа и вебхук остаются следующими этапами.
Промокоды хранятся в словаре «код → процент скидки», изначально `KVITTO10 → 10`.
Скидка рассчитывается как `price * percent // 100`: дробная часть копейки отбрасывается.
Для `card` и `sbp` переданный допустимый срок приводится к `null`.

## Создание и идемпотентность

- [ ] Новый платёж создаётся со статусом `pending`, ответ — `201`.
- [ ] Без ключа каждый корректный запрос создаёт отдельный платёж.
- [ ] Повтор одного ключа возвращает прежний платёж с `200`, без дубля.
- [ ] Одновременные запросы с одним ключом создают ровно одну запись в БД.
- [ ] Уникальность ключа обеспечена ограничением PostgreSQL.

## Чтение и статусы

- [x] Список тарифов и ответ с платежом содержат все поля контракта.
- [x] Время создания сериализуется с часовым поясом, суммы — целые, без рассрочки график — `null`.
- [x] Чтение неизвестного платежа возвращает `404`.
- [x] `GET /payments` фильтрует по email, статусу и их сочетанию; без совпадений возвращает `[]`.
- [ ] Вебхук для неизвестного платежа возвращает `404`.
- [ ] Разрешены `pending → succeeded`, `pending → failed`, `succeeded → refunded`.
- [ ] Остальные переходы, включая повтор текущего статуса, дают точный ответ `409`.
- [ ] При запрещённом переходе состояние БД не меняется.
- [ ] Успешный вебхук возвращает `200 {"result":"ok"}`.
- [ ] Проверка перехода и изменение статуса атомарны при конкурентных запросах.
- [ ] Каждая конкурентная задача использует свою сессию БД.
- [ ] Транзакции завершаются commit либо rollback.

## Бонусы и границы

Запуск через Docker Compose с PostgreSQL и управление сессиями реализованы.
Модели БД, начальная миграция Alembic и создание тарифов реализованы.
Реализованы `GET /tariffs` и `GET /payments/{id}` без префикса `/api/v1`.
Создание платежа и вебхук относятся к следующим этапам.
Собственные правила для ассистента уже представлены в `AGENTS.md`.

- [x] Приложение ожидает готовности PostgreSQL и проверяет подключение при старте.
- [x] Пароль БД берётся из окружения; `.env` не входит в образ.
- [x] Один engine на lifespan, отдельная сессия на запрос, engine освобождается.
- [x] Границы транзакций определены: сервис использует `session.begin()`, CRUD не коммитит.
- [x] Реальные тесты PostgreSQL проверяют commit, rollback и конкурентные сессии.

Бонус `GET /payments` с фильтрами по email и статусу реализован.
Отдельно предложены, но пока не реализуются: HMAC и GitHub Actions.
Если выбирается HMAC:

- [ ] `X-Signature` проверяется как HMAC-SHA256 исходных байтов тела.
- [ ] Сравнение выполняется через `hmac.compare_digest` до изменения БД.
- [ ] Отсутствующая или неверная подпись даёт `401` и не меняет БД.
- [ ] Отсутствующий или пустой `WEBHOOK_SECRET` запрещает запуск.

Фронтенд, авторизация пользователей, настоящий банк и деплой вне объёма задания.
Публикация репозитория и отправка ссылки не выполняются без отдельного разрешения.
